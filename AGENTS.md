# Agent Instructions

## Package Managers
- Backend: **Go** (`go build ./...`, `go vet ./...`)
- Frontend: **npm** (`npm install`, `npm run dev`, `npm run build`)

| Task | Command |
|------|---------|
| Go Typecheck/Lint | `(cd backend && go vet ./...)` |

## Commit Messages
- Use Conventional Commits: `<type>(<optional scope>): <description>`.
- Allowed types: `feat`, `fix`, `refactor`, `perf`, `style`, `test`, `docs`, `build`, `ops`, `chore`.
- Write the description in lowercase imperative present tense, without a trailing period (for example, `fix(api): validate migration ownership`).
- Use `!` before `:` for breaking changes and include a `BREAKING CHANGE:` footer. Use scopes for context, never issue IDs.
- Use the default Git messages for merge and revert commits.

## Architecture Overview
- **Two Go entrypoints**: `cmd/api` (HTTP API gateway) and `cmd/worker` (migration engine). Both share the same module `backend/`.
- **Queue**: PostgreSQL-native via `SELECT … FOR UPDATE SKIP LOCKED` in `queue.DequeueSQL()`: migrations dequeue in `RUNNING`/`INDEXING`; sync jobs dequeue only in `RUNNING` (their `INDEXING` phase builds a fresh delta). Each claimed sync pass increments `run_generation`; tasks persist that value as `pass_generation`, and lifecycle/progress updates require the matching generation. Final sync task statistics, the reconciled `sync_state` baseline, and the transition back to `IDLE` commit atomically; a baseline-write failure rolls back success and fails the pass for retry. On cancellation, the coordinator retains its cross-instance pass lock while workers drain, with a 30-second bounded grace period. Redis coordinates worker liveness, distributed schedule/recovery/OAuth locks, API rate limiting, and cancellation/bandwidth Pub/Sub; PostgreSQL remains the task queue.
- **Worker background schedulers** (all started by `processor.Start()`):
  - `RunWorkerLiveness` — heartbeat every 10 s, detects dead workers and reclaims their tasks
  - `RunRetryScheduler` — re-enqueues tasks whose `next_retry_at <= NOW()` every 10 s
  - `RunConnectionRecoveryScheduler` — probes up to 10 round-robin `PAUSED_CONNECTION_LOSS` migrations and 10 sync jobs every 60 s (with failure backoff); it re-activates migrations, while sync jobs only return to `IDLE` and make their active schedule due, so the API scheduler exclusively starts the pass
  - `RunOrphanedRunningTasksRecovery` — resets tasks stuck in `RUNNING` for > 10 min
  - `RunNotifier` — drains durable notification deliveries and cleans expired account tokens
  - `RunProgressReconciler` — reconciles migration and sync progress
  - `RunChecksumVerifier` — performs automated post-transfer verification for `VERIFYING` migrations and sync jobs every 10 s; PostgreSQL lease/generation fencing makes each verification pass single-writer across worker processes
- **OAuth daemon**: `RunOAuthRotationDaemon` in `cmd/api` rotates Dropbox, Google, OneDrive, and HiDrive refresh tokens for active migrations and sync jobs before expiry.
- **Public website**: `website/` is an independent static Vite package served separately from the authenticated SPA. In production, the public host must not be allowed by application CORS or proxy authenticated API routes.
- **Core Scheduler Engine**: A background daemon in `cmd/api` (`scheduler.Run`) checks for due schedules every minute and triggers linked migration or sync jobs. It uses `github.com/robfig/cron/v3` for cron parsing/next-run calculation. Schedules live in the `schedules` table; a Redis `SET NX` lock (`schedule:lock:{id}`, 2-min TTL) ensures only one API instance triggers a given schedule in a multi-instance deployment. The schema reserves `backup`, but backup triggering is not implemented.
- **Orphaned sync-job recovery**: `scheduler.RunOrphanedSyncJobRecovery` (API) resets sync jobs stuck in `INDEXING` (>30 min stale) or `RUNNING` (>30 min stale **and** no non-terminal task updated in the last 10 min) back to `IDLE`, records a recovery `error_message`, advances the linked active schedule, and uses a Redis `SET NX` lock (`sync:orphaned-recovery-lock`) so only one API instance recovers per tick. Needed because sync passes run as API goroutines — workers cannot unwedge a dead coordinator.
- **Indexer package**: `backend/internal/indexer` holds the shared indexing logic (`Indexer.Start`). Both the immediate `handleStart` path and the scheduler's `triggerMigration` call it, so scheduled migrations actually create PENDING tasks. Selected paths/calendars/contacts are persisted on the `migrations` row (`selected_paths`/`selected_calendars`/`selected_contacts` JSONB) and read at trigger time.
- **Migration detail SSE auth**: `/api/migration/{id}/stream` is behind `AuthMiddleware`, receives its JWT only in the `Authorization: Bearer` header, and validates ownership from the request context. No realtime endpoint accepts access tokens in query parameters.
- **Transfer & conflict resolution**: Files use `SKIP` (with size-match short-circuit), `OVERWRITE`, or `RENAME` (up to 100 suffix attempts). `OVERWRITE` stages to `.tmp` and promotes atomically only when `SupportsAtomicRename()` is true; non-atomic targets (including S3, Seafile, and Immich) upload directly to the final path. Filename sanitization (`internal/sanitize`) and case-collision resolution run first for case-insensitive targets. Immich requires native duplicate `SKIP` and does not support overwrite, rename, or delete. Calendars/contacts are always overwritten (a `SKIP` would leave stale entries). Transfers are streamed through a RAM buffer (zero disk retention); files > 50 MB use chunked upload.
- **Data integrity (3-way hash check)**: An `io.TeeReader` computes provider-specific hashes while streaming (`SHA1` default; `MD5`/`SHA256`/`DROPBOX`/`QUICKXOR` as applicable). When the target uses a different native algorithm, its streaming hash (including HiDrive `HIDRIVE` `chash` and OneDrive `QUICKXOR`) is retained for comparison with the server-side target hash; HiDrive source-to-target compares native hashes directly. The provider decodes URL-escaped API response paths before indexing to prevent double-escaped 404s. Where hashes cannot be compared, fall back to size comparison to avoid false "corrupted" verdicts.
- **Completion notifier & reports**: `RunNotifier` (worker) drains the durable per-channel notification outbox (email, Gotify, ntfy, Telegram, Discord), retrying each delivery independently; it also cleans expired reset/email-change tokens. `email_sent` remains a legacy column. `GET /api/migration/{id}/report` returns a CSV report (failed tasks + skipped indexing errors); spreadsheet formula-injection chars are neutralized server-side.
- **Instance mailer**: SMTP is a single administrator-managed `instance_smtp_settings` row encrypted with `ENCRYPTION_SECRET_KEY`; it is never configured through `SMTP_*` environment variables or user settings. Completion email is enabled by default when the instance mailer exists; a saved per-user email preference can explicitly opt out. Reset, email-change, tests, and outbox deliveries load the current instance configuration and decrypt it immediately before use.
- **Instance OAuth providers**: Google/OneDrive/Dropbox/HiDrive client credentials live in the administrator-managed `instance_oauth_providers` table (secret encrypted with `ENCRYPTION_SECRET_KEY`); they are never configured through `*_CLIENT_ID`/`*_CLIENT_SECRET` environment variables. Both entrypoints install `oauth.Configure(oauth.NewDBLoader(db), key)` after DB init; the process-local cache holds only ciphertext (30 s TTL) and the API invalidates it on write. The OAuth redirect URI is always `<scheme>://<host>/api/oauth/callback` and is not configurable.

## Key Conventions

### Database
- Schema changes must be added to [schema.sql](db/schema.sql) **and** as an inline `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE … ADD COLUMN IF NOT EXISTS` statement inside `InitDB()` in [db.go](backend/internal/db/db.go) for automatic migration on startup.
- All DB queries must use parameterised statements (`$1`, `$2`, …) — never string-interpolate user input into SQL.

### Storage Providers
- For Seafile username/password connections, workers share an in-memory account-token cache per server/account. A single in-flight authentication is allowed for each cache key; HTTP `429 Too Many Requests` honors the server's `Retry-After` value before another authentication is attempted. Tokens are never persisted by this cache and are removed when the server rejects them with `401` or `403`. Seafile streaming uploads retain SSRF-safe egress validation and redirect rejection, but have no total request deadline; connection setup remains bounded and a response must arrive within five minutes after the upload body is sent.
- `mega` is an additional whitelisted provider. It is a files-only personal Cloud Drive provider: it uses email/password with forced HTTPS, persists reusable session ID and master-key material encrypted, excludes MFA accounts, rejects ambiguous same-name siblings, and uses size-only verification.
- Every provider must implement the `StorageProvider` interface in [provider.go](backend/internal/storage/provider.go) and be registered in [factory.go](backend/internal/storage/factory.go). The interface is required (no optional methods), so every new provider — and every test mock — must implement all methods, including `SupportsAtomicRename() bool` (return `true` only for atomic "upload-to-`.tmp`-then-promote" overwrite; return `false` when promotion is non-atomic or unsupported, so the processor uploads directly to the final path) and `VerificationMode() VerificationMode`. Use `cryptographic_hash` only for comparable target hashes; ETag-only or hashless targets (including Nextcloud/WebDAV/MagentaCLOUD and Seafile) must use `size_only`, which skips `GetFileHash` and verifies existence and size. Immich uses its target asset ID plus Base64 SHA-1 checksum (normalized as `SHA1:<hex>`), with an asset-ID size fallback; ETags are never integrity evidence, and historical tasks without the persisted target ID remain unverified. Omitting either method breaks the build.
- Valid provider values: `nextcloud`, `opencloud`, `webdav`, `dropbox`, `google`, `onedrive`, `hidrive`, `smb`, `s3`, `sftp`, `ftp`, `magentacloud`, `local`, `immich`, `seafile`, `mega`. Whitelist these explicitly — never pass unvalidated provider strings to `NewProvider`. `ftp` is files-only FTPS: accept only explicit `ftp://host:21?tls=explicit` or implicit `ftps://host:990`; reject plain FTP and URL userinfo. Use standard CA validation with hostname/SNI; do not allow certificate-validation bypasses or custom CAs. Its control and passive data connections use the DNS-rebinding-safe egress dialer; EPSV is preferred and PASV uses only the announced port with the validated control host, never the announced address. FTP provides no portable hashes, so integrity verification falls back to size comparison. SMB requires message signing; the dependency uses SMB3 encryption when the server/share requires it, but cannot require it client-side, so use SMB only on trusted networks unless the server/share enforces encryption. OneDrive uses fixed Microsoft Graph endpoints, personal accounts only, and supports files plus shared-folder shortcuts by resolving their remote drive/item identity; Personal Vault is detected from its `specialFolder` facet and skipped because its interactive unlock cannot run in a background OAuth job. SharePoint, calendars, and contacts are unsupported. File verification uses Graph's non-cryptographic QuickXor hash when available. SFTP URLs must carry a trusted `host_key` SHA-256 fingerprint and the SSH handshake must reject any other host key. `local` requires no credentials (no URL/username/password); on Unix-like hosts, it reads/writes only inside the server-derived tenant namespace `LOCAL_STORAGE_ROOT/users/<user-id>` using root-anchored, component-by-component `openat`/`O_NOFOLLOW` traversal for every operation, preventing symlink replacement races. Mutations are intentionally unavailable on Windows pending an equivalent handle-relative implementation. It supports only `files` (calendars/contacts not applicable). The user ID must come from JWT claims or the persisted job owner; creating a local provider without this scope must fail. `immich` uses a server URL plus API key in the encrypted password field (no username), supports files-only one-time migrations, virtual `/Timeline` and `/Albums` source browsing, native duplicate `SKIP`, and no atomic rename. An Immich target maps a single target-directory name to an album; nested target directories are unsupported. It is shown in the UI only when `LOCAL_STORAGE_ROOT` is configured (`local_storage_enabled` in `/api/settings`); `NewProvider("local")` errors if unset. `seafile` uses a server URL plus user/pass or API token, supports files-only zero-disk retention migrations/syncs, and uses `size_only` verification: its API exposes Seafile object IDs, not a comparable SHA-1 hash of the complete file content. Applies egress validation to `nextcloud`/`webdav`/`smb`/`sftp`/`ftp`/`immich`/`seafile`.
- Resource types: `files`, `calendars`, `contacts`. Calendars/contacts are always overwritten on conflict (dynamic data — SKIP would silently leave stale entries).
- User-configured HTTP providers (Nextcloud, OpenCloud, WebDAV, Immich, Seafile, and custom S3 endpoints) require HTTPS. Plaintext HTTP and the former S3 `insecure=true` exception are unsupported.

### Security
- **Credential handling**: Never pass plaintext credentials to background goroutines. Query from database by `MigrationID` and decrypt at the last moment using `crypto.Decrypt`.
- **Error messages**: Never forward raw `err.Error()` strings for connection failures to API responses (may embed URLs with embedded credentials). Log through structured `slog` after redaction, and return only a machine-readable `error_code` (see API Response Patterns) - never a human-readable/English message.
- **Structured logging**: API and worker processes emit JSON `slog` records to stdout. `LOG_LEVEL` accepts `DEBUG`, `INFO`, `WARN`, or `ERROR` (case-insensitive) and defaults to `INFO`; `LOG_ENVIRONMENT` is an optional deployment label and `INSTANCE_ID` an optional stable per-replica identifier. API request IDs appear in request logs and the `X-Request-ID` response header. Redact URL userinfo, sensitive headers, passwords, keys, tokens, secrets, and equivalents; never log request/response bodies. Paths are personal metadata: omit them normally, and use `DEBUG` path logging only temporarily because it is a privacy risk. Log an error once at its handling boundary with context and request ID; propagate/wrap without logging it again, while clients receive only an `error_code`.
- **Key Segregation**: Use `ENCRYPTION_SECRET_KEY` exclusively for AES-256-GCM encryption/decryption (`crypto.Encrypt` / `crypto.Decrypt`). Use `JWT_SECRET_KEY` exclusively for JWT signing. The API server **refuses to start** if either is missing.
- **AES-256-GCM key derivation**: The raw secret is SHA-256-hashed inside `crypto.deriveKey` to produce a 32-byte key — any length secret is accepted; the hash is the actual key.
- **OAuth2 Credentials**: OAuth2 access tokens and refresh tokens are stored AES-GCM encrypted on migration and sync-job rows (`source_refresh_token_encrypted`, `target_refresh_token_encrypted`). The `RunOAuthRotationDaemon` in the API gateway rotates them automatically before expiry.
- **Token Rotation**: Login-session refresh tokens are consumed and replaced inside one database transaction. OAuth token pairs are encrypted and conditionally persisted atomically against the previous refresh-token ciphertext, so a failed persistence does not discard a still-valid provider token.
- **Refresh-token sessions**: Refresh tokens are stored only as hashes; each session has a public ID and capped User-Agent label. Authenticated users can list only their active session metadata and revoke an individual session by ID without cross-account existence disclosure.
- **CORS Whitelisting**: Never reflect incoming CORS origins or allow credentials for wildcards. Use the static `allowedOrigins` map (hardcoded localhost variants + `CORS_ALLOWED_ORIGIN` env var). Unknown origins receive no `Access-Control-Allow-Origin` header.
- **Redis Security**: Redis requires password authentication (`REDIS_PASSWORD` env var). Connection string format: `redis://:$REDIS_PASSWORD@redis-queue:6379`. Redis is **not** exposed to the host network. `NewQueue` rejects empty or known-default passwords (`redis_secret`, `dev_redis_secure_pass_999`).
- **SSRF Protection**: User-supplied provider URLs are validated by `storage/ssrf.go` (`validateEgressURL` / `ValidateEgressHost`) before any egress. Loopback (`127.0.0.0/8`, `::1`) and link-local (`169.254.0.0/16`, incl. cloud metadata `169.254.169.254`) are always blocked. RFC1918/ULA private ranges are blocked only when `MIGRATION_BLOCK_PRIVATE=1` (permitted by default for self-hosted/internal servers). DNS-rebinding (TOCTOU) is mitigated by re-resolving and re-validating the address inside `egressDialer.DialContext` immediately before each connection while keeping the real hostname for TLS SNI/cert validation; the transport rejects a different dial host. User-configured provider, S3, and notification clients do not follow redirects. `providerRegistry` is the source of truth for HTTPS-only and SSRF-validated provider URL requirements; custom S3 endpoint validation remains in the S3 provider. Egress validation applies to `nextcloud`/`opencloud`/`webdav`/`smb`/`sftp`/`ftp`/`immich`/`seafile`.
- **Request body limits**: JSON request bodies are decoded through `http.MaxBytesReader`; normal API JSON is limited to 1 MiB, avatar JSON to 3 MiB (for the existing 2 MiB decoded-image cap), and authentication/TOTP JSON to 64 KiB. Oversized or malformed bodies return `INVALID_BODY`, except password-reset requests retain their generic success response for anti-enumeration.
- **Rate Limiting & Lockouts**: A Redis-backed fixed-window limiter keyed by endpoint group and client IP (honours `X-Forwarded-For` only behind a trusted proxy — see `TRUSTED_PROXY`) provides consistent multi-instance limits without cross-throttling endpoint groups. Limits: Login 10/min, Register 5/5min, Connect/Browse/Mkdir and session list/revoke 30/min, Migration/sync create or start 10/min, TOTP 10/min, migration stream (SSE) 60/min with max 10 concurrent streams per user. 5 failed logins → 15-min lockout; 5 failed TOTP attempts → 15-min lockout (both atomic, in `db`).
- **Security Headers**: `securityHeadersMiddleware` (wrapping `corsMiddleware`) sets `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` (the OAuth callback sets its own nonce-based CSP), and `Strict-Transport-Security` over HTTPS, including `X-Forwarded-Proto: https` only when `TRUSTED_PROXY` is enabled. API server timeouts: read 30s, write 60s, idle 120s; long-lived SSE handlers clear their individual write deadline via `http.ResponseController`.
- **Audit Logging**: A best-effort `audit_log` captures security-relevant events (logins, migration lifecycle, user management, 2FA changes, settings updates) via `db.AuditAction` constants. `ip` values are sanitized (control/CR-LF stripped, CWE-117). Writes never block the primary request.
- **2FA / TOTP**: TOTP 2FA is optional per user (`/auth/2fa/*`). Setup returns secret/QR; enable requires verifying a code + storing single-use backup codes; a backup code used to disable 2FA is removed before the disable operation continues. Lockout after 5 failed attempts for 15 minutes (`db.IncrementTOTPFailed`). `AuthMiddlewareAllowMustChange` lets users with `must_change_password` reach the change-password endpoint.
- **Admin Setup & Roles**: Roles are `USER` (default) and `ADMIN`; admin endpoints enforce `role == ADMIN` inside the handler. Initial setup triggers when no users exist in the database (`COUNT(*) == 0`). The Web UI prompts the user to create an initial administrator account (`POST /api/auth/setup-admin`). Once created, setup is permanently locked and subsequent setup requests return `403 Forbidden` (`SETUP_ALREADY_COMPLETED`). Suspending a user pauses their active migrations and sync jobs, cancels in-flight sync coordinators/transfers, and disables schedules; reactivating re-enables schedules.
- **Startup refusal contract**: Both API and worker refuse to start if `ENCRYPTION_SECRET_KEY` is empty, `REDIS_PASSWORD` is empty or a known default, or the DB DSN uses `postgres:postgres@` on a publicly reachable host. The API additionally refuses an empty `JWT_SECRET_KEY`, one equal to `ENCRYPTION_SECRET_KEY`, or one shorter than 32 bytes; the worker does not use a JWT key.

### Multi-Tenancy & Ownership
- All endpoints operating on a specific migration (`GET /api/migration/{id}`, `DELETE /api/migration/{id}`, `GET /api/migration/{id}/report`) must call `auth.GetUserIDFromContext(r.Context())` and compare against `mig.UserID` — return `403 Forbidden` on mismatch.
- The detail SSE handler (`/api/migration/{id}/stream`) is JWT-protected and performs the same ownership check from the request context.
- User ID is always sourced from the validated JWT claims injected by `AuthMiddleware` via `auth.ClaimsKey` context key.
- Schedule endpoints (`GET /api/schedule/{id}`, `DELETE /api/schedule/{id}`) verify ownership via `db.VerifyScheduleOwnership` (uses `EXISTS`, never returns `sql.ErrNoRows`). A non-owning result means the schedule either does not exist or belongs to another user — return `404 Not Found` in both cases to avoid leaking existence/ownership (do **not** return `403`).

### Indexing (BFS)
- Use queue-based Breadth-First Search with a `visited` map for recursive directory traversal to prevent infinite loops on symlink cycles or circular DAVs.
- Track indexed paths with a `resourceType:path` key in an `indexedPaths` map to prevent duplicate tasks.
- Indexing is resilient: a single folder/file error is recorded in `indexing_errors` and skipped rather than aborting the whole migration; per-folder errors surface in the final report.
- `sanitizeError` redacts `user:pass@` from any URL embedded in error strings before persisting to `migrations.error_message` / `indexing_errors` (see Security -> Error messages).

### Scheduler Engine
- **Schedule table**: `schedules` (id, user_id, task_type, task_id, cron_expression, run_at, next_run_at, is_active). One-shot jobs leave `cron_expression` NULL and set `run_at`/`next_run_at`; cron recurring jobs compute `next_run_at` via `cron.ParseStandard`. Sync jobs also leave `cron_expression` NULL and advance `next_run_at` by their persisted `interval_minutes`, so intervals such as 90 minutes are valid.
- **Trigger loop**: `scheduler.Run` ticks every 1 min, calls `GetDueSchedules` (`is_active = TRUE AND next_run_at <= NOW()`), claims each via Redis `SET NX` (`schedule:lock:{id}`, 2-min TTL), then `processSchedule`.
- **Overlap protection**: Before triggering, `isJobActive` checks the linked job's status. `RUNNING`/`INDEXING`/`VERIFYING`/`PAUSED_CONNECTION_LOSS` ⇒ skip (log + advance `next_run_at` for recurring). `VERIFYING` retains ownership of its current pass; `PAUSED_CONNECTION_LOSS` remains reserved for connection recovery. This satisfies the "90-min sync skipped at 60 min" acceptance criterion.
- **Lifecycle**: One-shot ⇒ `DeactivateSchedule` after trigger. Cron recurring jobs ⇒ recompute `next_run_at` via `NextRun(cron_expression)`; sync jobs ⇒ add `interval_minutes` to the current time.
- **Failure handling**: If `triggerJob` errors (e.g. linked task deleted, migration not in `SCHEDULED` state), the schedule is **deactivated** to prevent an infinite retry loop. The user re-creates it via the API if needed.
- **Deferred migrations**: `handleStart` with `scheduled_time` creates the migration in `SCHEDULED` status + a one-shot schedule. The scheduler's `triggerMigration` calls `indexer.Start`, which reads persisted `selected_paths`/`calendars`/`contacts` and creates PENDING tasks — scheduled migrations actually execute (no silent stall in `SCHEDULED`/`INDEXING`).
- **Cron validation**: Validate user-supplied cron expressions with `scheduler.ValidateCronExpression` (wraps `cron.ParseStandard`) before persisting.

### API Response Patterns
- Use `writeJSON(w, status, data)` for all JSON responses — never write raw JSON manually.
- **Machine-readable error codes (i18n)**: Every error response carries only a machine-readable `error_code` (no human-readable text). Use the typed `APIErrorCode` enum with `writeError(w, status, code)`, `writeValidationError(w, code)` (400), or `writeConflictError(w, code)` (409). Add every new code to the `APIErrorCode` constant block AND to both frontend locale files; the backend never localizes.
- Connection-test endpoints (`/connect`, `/browse`, `/target/browse`, `mkdir`) return `HTTP 200` with `{"success": false, "error_code": "..."}` for logical failures (not `4xx`) so the frontend displays the localized message via `translateApiError`.
- Never return raw `err.Error()` strings or use `http.Error(w, msg, 4xx)` for client-facing errors - this leaks internals (e.g. URLs with embedded credentials). See Security -> Error messages.
- **CSV report safety**: The migration report neutralizes spreadsheet formula-trigger characters (`=`, `+`, `-`, `@`, tab, CR) by prefixing cells with a single quote, since paths/errors originate from the (attacker-influenced) source server.

### Internationalization (i18n)
- **Library**: Frontend uses `i18next` + `react-i18next` + `i18next-browser-languagedetector`, initialized in `src/i18n.ts`. Supported languages: `de`, `en` (fallback `en`).
- **Translation files**: `src/locales/{de,en}/translation.json`. Both files MUST stay in key parity - every key present in one must exist in the other (run a structural diff after editing either file).
- **Error codes**: Backend `error_code` values are localized under the `errors.*` namespace (e.g. `errors.MIGRATION_NOT_OWNED`). When adding a new `APIErrorCode`, add the matching `errors.<CODE>` entry to BOTH locale files. Unmapped codes fall back to `errors.UNKNOWN` via `translateApiError`.
- **Consuming error codes**: Components call `useApiError()` (from `src/utils/apiError.ts`) to obtain `translateApiError`, then call `translateApiError(data.error_code)`. Do NOT read raw `error`/`message` fields from API responses.
- **API error parsing**: Read `error_code` from the JSON body, e.g. `const body = await res.json().catch(() => ({})); translateApiError(body.error_code)`.
- **Formatting**: Locale-aware number/date/bytes formatting lives in `src/utils/format.ts` (`formatBytes`, `formatDate`, `formatDateTime`, `useFormat`). Never hand-format with `toFixed`/`toLocaleString` without passing the active language.
- **Language switcher**: `src/components/LanguageSwitcher.tsx` lets users switch; the choice is persisted to `localStorage` by the detector.
- **Delivery language**: The selected `de`/`en` value is also persisted on the user account and determines all emails and notification channels.
- **Backend delivery catalog**: E-mail and notification text lives under `delivery.*` in the frontend locale files. Docker build stages regenerate the checked-in Go catalog automatically before compiling; run `(cd backend && go generate ./internal/i18n)` only before a direct local `go build`.

### Frontend UI
- Use semantic `ui-*` utilities and the light/dark tokens in `frontend/src/index.css`; do not reintroduce `portal-*`, `glass-*`, `shadow-portal*`, decorative gradients, blur, large shadows, or scale hover effects.
- Use `@heroicons/react` for application UI/action icons. `react-icons` is limited to provider-brand icons in `components/connect/ProviderIcon.tsx`. Icon-only actions need localized `aria-label` and `title`.
- Prefer native controls. Keyboard-operable tabs, menus, dialogs, and trees are required; dialogs need a name, modal semantics, Escape, focus trapping, and focus restoration.
- For frontend changes also run `(cd frontend && npm test)` and `(cd frontend && npm run build)`, and verify locale key parity whenever translations change.

### Threads & Parallelism
- `threads` per migration or sync job is capped at 1–16. The worker respects this via the SQL dequeue query (`COUNT(*) < m.threads`). Sync jobs also persist a 0–1000 Mbps bandwidth limit (0 is unlimited), which can be updated live.
- Worker-level concurrency is set by `MAX_THREADS` env var (default: 16, matching the max selectable per-migration threads slider). This is the total parallel tasks per worker process, not per migration.

### Retry & Backoff
- Exponential backoff: $10 \times 3^{\text{attempt}}$ seconds (10 s → 30 s → 90 s), max 3 attempts.
- Permanent errors (e.g. expired/invalid OAuth token, irrecoverable auth failure) skip retry immediately and mark the task `FAILED`.
